# StakeOS v1.2.1

A bug-fix release for the MCP tools. Five defects made member lookups either crash,
return wrong names, or silently return nothing. Two of the affected tools were unusable
in every case, not just edge cases.

No sync is required — these are all query-side fixes.

## Highlights

### Fixes

- **`resolve_member` failed on every query.** The lookup built 12 SQL parameters for a
  statement with 10 placeholders, so SQLite rejected it before it ran with
  `Too many parameter values were provided`. The two parameter groups were also ordered
  backwards relative to how SQLite binds them (the `SELECT` scoring clause binds before
  the `WHERE` clause). Resolving a member by name, email, phone, or LCR id now works,
  including with the `unit` filter.

- **`member_profile` crashed with `no such column: c.organization`.** The callings query
  selected a column that does not exist — the `callings` table stores
  `organization_name`. The tool returned an error instead of a profile for every member.

- **Member names showed the surname twice.** Tools built display names by treating
  `preferred_name` as a first name and appending the last name — but LCR stores
  `preferred_name` in `"Last, First"` form, so "Linda Bennett" came back as
  "Bennett, Linda Bennett". This affected **4,217 of 4,222 members** and appeared in 17
  places across `member_profile`, `ministering_assignments`,
  `reverse_ministering_lookup`, `upcoming_birthdays`, `unit_ministering_coverage`, and
  spouse lookups.

- **`upcoming_birthdays` always returned an empty list.** The query read the month and
  day by character offset, assuming an ISO `YYYY-MM-DD` date. LCR supplies birthdates as
  `17 Aug 1957`, so the offsets produced garbage, every row computed a `NaN` day count,
  and every member was filtered out. Dates are now parsed with the same helper the rest
  of the app already uses, which accepts both formats. Ages were affected the same way
  and are correct again.

- **Birthdays landing today were reported as a year away.** A separate defect in the same
  tool compared a midnight date against the current time-of-day, so a birthday *today*
  counted as already passed and rolled forward to next year.

- **`reverse_ministering_lookup` could not match anyone.** It searched the stored
  ministering assignments for `"First Last"`, but LCR writes those entries as
  `"Last, First"` joined by `/`, so the search never matched. It now compares canonical
  name variants, the same approach already used elsewhere in the app, and matches either
  name order.

## Action Required After Updating

None. No schema or sync changes — the corrected results appear immediately.

## Install Notes

- Download the `.dmg` for the standard macOS install flow.
- Use the `.zip` if the DMG is blocked or you need the app bundle directly.
- This build is unsigned and not notarized. If macOS blocks first launch, right-click the
  app and choose **Open**, or use **System Settings > Privacy & Security > Open Anyway**.
- If macOS still blocks it, run
  `xattr -dr com.apple.quarantine "/Applications/StakeOS Desktop.app"` and try again.
- Windows users: see
  [WINDOWS_DASHBOARD_SETUP.md](https://github.com/naugsco/stakeos/blob/main/WINDOWS_DASHBOARD_SETUP.md).
  Windows runs from source, so pull this version to get these fixes.

## Suggested Validation

- Ask for a member profile by full name and confirm it returns rather than erroring, and
  that the name reads "First Last" rather than repeating the surname.
- Ask for upcoming birthdays and confirm the list is non-empty and that anyone whose
  birthday is today appears first.

## Known Limitations

- `reverse_ministering_lookup` and `unit_ministering_coverage` return nothing until a
  sync populates the ministering columns, which are currently empty for all members. The
  matching logic is fixed and was verified against seeded data, but there is no live
  ministering data to read yet.
- Members born on 29 February are treated as 1 March in non-leap years. Unchanged
  behaviour.
- The `package-lock.json` version field still reads `1.0.19`; it has not tracked the app
  version since v1.0.19 and does not affect the build.
